# Configurable ICU Mortality Landmark Cohorts

This document describes the cohort construction implemented by
`R/mortality_landmark.R` for the `hirid` and `miiv` sources. It is intended to
make the operational target reproducible and to separate confirmed processing
behavior from assumptions and scientific limitations.

The task reuses YAIB-cohorts infrastructure and the canonical hourly base
cohort. It does not create a new raw-data extraction framework. The output is a
benchmark-compatible ICU-stay-level dataset, with a source-level outcome
metadata table used to construct labels and W/H-specific prediction files.

## A. Research task and estimand

The prediction unit is an ICU stay identified by `stay_id`. Let (s) denote a
stay and let time be measured relative to the operational ICU admission/start
time supplied by ricu. The configurable task has two parameters:

- (W): the last included hourly bin index;
- (H): the prediction horizon in hours.

The prediction landmark is

\[
a(W) = W + 1\text{ hour},
\]

and the horizon endpoint is

\[
b(W,H) = W + 1 + H\text{ hours}.
\]

The model input covers the half-open physical interval

\[
[0, a(W)),
\]

and the operational mortality target is ICU death in

\[
(a(W), b(W,H)].
\]

Thus, for an eligible stay,

\[
Y_s(W,H) = \mathbf{1}\{a(W) < \tilde d_s \le b(W,H)\},
\]

where (	ilde d_s) is the one-minute-discretized event time used by the
pipeline. The tilde is important: the implementation does not claim to retain
or recover exact clinical death timestamps.

Eligibility is defined before the label is written. A stay must be in the
selected canonical base cohort, have a valid ICU window, remain in the ICU past
the landmark, have an interpretable outcome state, and have an event time when
the outcome state is dead. Stays with unknown outcomes or uncertain timing are
excluded by the default `unknown_policy = "exclude"`.

For W=24 and H=12:

- observation: `[0, 25)` hours;
- prediction interval: `(25, 37]` hours.

For W=36 and H=12:

- observation: `[0, 37)` hours;
- prediction interval: `(37, 49]` hours.

W is not an exact duration of 24 or 36 hours. It identifies the last included
hourly bin. This W+1 convention is inherited from the YAIB hourly-bin
representation and is preserved intentionally.

## B. Observation-window convention

The implementation uses `stay_windows()`, `as_win_tbl()`, `stop_obs_at()`,
`map_to_grid()`, and the existing frequency helpers. The context cutoff is
calculated as the prediction start minus one feature interval. The resulting
grid includes the bin at zero and ends at `prediction_start - interval`.

For W=24/H=12, the expected bin starts are:

| Feature frequency | Physical grid | Last included bin | Bins per stay |
|---|---:|---:|---:|
| 1h | `[0, 25)` h | 24h | 25 |
| 15min | `[0, 25)` h | 24h45m | 100 |
| 5min | `[0, 25)` h | 24h55m | 300 |

For W=36/H=12, the corresponding counts are 37, 148, and 444. All feature
frequencies therefore cover the same physical observation period. A finer
frequency changes the representation of measurements, not the estimand or the
outcome window.

The dynamic path performs a left merge from the expanded patient grid to the
loaded concepts. Missing bins remain missing. There is no separate context
window implementation and no future bin at or after the prediction start. The
synthetic tests exercise this at all three supported frequencies.

The one-minute outcome metadata interval is independent of the feature
frequency. Labels are constructed once from source metadata and reused only
after applying W/H-specific eligibility and labeling.

## C. Cohort selection and eligibility

### Canonical base cohort

The task first reads the canonical hourly base-cohort stay IDs from
`base/{source}/sta.parquet`. The base cohort is generated by `R/base_cohort.R`.
For the hourly canonical cohort, its code applies the following exclusions:

1. **Invalid ICU length of stay:** the operational ICU window has `end < 0`.
2. **Short ICU stay:** `los_icu < 6/24` days, i.e. less than six hours.
3. **Insufficient dynamic observations:** the loaded canonical dynamic table
   has fewer than four rows under the `summary_step(..., "count")` operation.
4. **Long observation gaps:** the dynamic table is placed on the hourly
   eligibility grid, converted to observed/not-observed rows, and the longest
   run without observations is rejected when it is greater than the 12-hour
   threshold used by the code.
5. **Age below 18:** the `age` concept is less than 18.

For non-hourly base outputs, the code reuses the hourly canonical eligibility,
static IDs, and attrition rather than recomputing the seven-day eligibility
rules at the finer frequency. The configurable mortality task similarly uses
the canonical base IDs for compatibility with YAIB and earlier experiments.

This choice is deliberate but not strictly prospective for a landmark task.
Several canonical exclusions are defined using the seven-day base window or
observations that can occur after the mortality landmark, especially the
measurement-count and long-gap rules. The resulting cohort is therefore a
benchmark-compatible selected cohort, not a cohort selected using only data
available at the landmark.

The older `R/mortality.R` task adds mortality24-specific exclusions for death
within the first 30 hours and ICU length of stay below 30 hours. Those rules are
not reused by the configurable landmark task. Reusing them would impose a
fixed mortality24 selection rule on other W/H estimands.

### Additional landmark-specific eligibility

After source metadata is restricted to canonical base IDs, the landmark label
layer excludes a stay when any of the following applies:

- ICU start or end is missing, or the ICU window is invalid;
- the outcome status is neither `alive` nor `dead`;
- a dead outcome has no event-time proxy/timestamp;
- an alive outcome nevertheless has a death timestamp;
- ICU discharge/end is at or before the prediction start;
- ICU admission/start is after the prediction start;
- death is at or before the prediction start;
- death is before ICU start;
- death is after ICU end.

The last two checks prevent an event outside the selected ICU interval from
being treated as an ICU death for that stay.

## D. Mortality label construction

The source metadata table contains one row per stay with the operational ICU
window, event time when available, outcome status, event-time kind, ICU-end
kind, and timestamp-resolution fields. It is stored separately from model
features.

The default policy is:

- **Positive:** the discretized death event is strictly after the landmark and
  at or before the horizon endpoint, and lies within the ICU window.
- **Negative:** the stay is eligible, has no death in the prediction interval,
  and is not otherwise uncertain. An alive discharge during the horizon is a
  negative, provided the stay was still in the ICU at the landmark.
- **Excluded:** death at or before the landmark, missing/unknown outcome,
  missing dead-event time, invalid ICU timing, admission after the landmark,
  or an event outside the selected ICU window.

Boundary examples for W=24/H=12 are:

| Event | Operational result |
|---|---|
| Death at 25h exactly | Excluded as occurring at the landmark |
| Death immediately after 25h, if represented after the landmark | Positive |
| Death at 37h exactly | Positive |
| Death after 37h but before ICU end | Negative |
| Death after ICU end | Excluded as outside the selected ICU stay |
| Alive discharge before or at 25h | Excluded |
| Alive discharge during `(25,37]` | Negative |
| Unknown outcome status | Excluded |

The existing mortality24 30-hour exclusion is not reused because it is a
fixed-task cohort rule, not part of the general W/H estimand.

## E. MIMIC-IV mortality event definition

The configured `death_icu` concept uses MIMIC-IV `admissions` fields:

- `deathtime` as the event index;
- `hospital_expire_flag` as the hospital-death indicator.

The ricu MIIV source configuration defines `hadm_id` as the hospital-admission
ID and `stay_id` as the ICU-stay ID, with `icustays.intime` and
`icustays.outtime` defining the ICU window. MIMIC-IV hospital `transfers`
contains `hadm_id`, `eventtype`, `careunit`, `intime`, and `outtime`.

The current `miiv_death_icu()` callback now:

1. loads hospital transfers explicitly by `hadm_id`;
2. loads their time axis at one-minute resolution;
3. converts transfers from hospital-admission IDs to ICU-stay IDs with
   `change_id(..., "icustay", ..., id_type = TRUE)`;
4. renames `careunit` to the callback's `ward` field;
5. applies the shared last-care-unit rule in `mi_death_icu()`.

The shared rule marks a death as ICU mortality only when the final mapped care
unit for the selected ICU stay is an ICU. A hospital death associated with a
ward or another non-ICU final care unit is not an ICU death. Multiple ICU stays
within one admission are handled only after the transfer history has been
mapped to stay IDs; the callback must not assign the same hospital-death event
to every ICU stay in the admission.

The timestamp and the ICU interval are distinct pieces of information. The
event time is retained from `deathtime` after ricu's relative-time conversion,
while ICU start/end come from the stay window. The label layer excludes an
event before ICU start or after ICU end. A hospital death after ICU discharge is
therefore not silently relabeled as an ICU death for that stay.

### Previous versus current callback

The previous MIIV callback loaded transfers without explicitly selecting
`hadm_id` or converting them to ICU stay IDs. That was inconsistent with the
MIMIC-III callback and with ricu's item-loading behavior, where the admission
death concept is requested at `icustay` ID type. The previous path could compare
hospital-admission transfer IDs with ICU-stay death IDs and fail to attribute
multi-stay events correctly.

The correction is in the shared `death_icu` callback used by the legacy
`mortality.R` path as well as the landmark path. Consequently, MIIV
`mortality24` output can change where the old callback failed to perform the
hospital-to-ICU mapping. This is a correction of an existing ID-attribution
bug, not a deliberate change to the mortality24 estimand. `R/mortality.R` and
its fixed 30-hour task rules remain otherwise unchanged. A real-data regression
comparison is still required before treating old and new MIIV mortality24
files as numerically identical.

The repository currently lacks configured MIIV data, so the real ricu
`change_id()` path could not be executed against source-backed synthetic
tables. Source configuration and ricu method definitions were inspected. The
tests exercise the shared attribution logic and the MIIV wrapper's required
`hadm_id`/`change_id` contract with fabricated transfer histories, but this is
not a substitute for a full source-backed mapping test.

## F. HiRID mortality event definition

The HiRID `death_icu` concept uses observation variable IDs 110 and 200,
corresponding to MAP and heart rate in the existing callback configuration.
`hirid_death_icu()` takes the last timestamp among those observations for each
stay and joins it to `general.discharge_status`. Only a discharge status of
`dead` produces a death event.

The configurable task also loads `general.discharge_status` directly for the
outcome state. Statuses are normalized to `dead`, `alive`, or `unknown`.
Unknown or missing status is not treated as alive. A dead stay without a valid
MAP/heart-rate timestamp has a missing event time and is excluded rather than
being assigned an invented time.

For HiRID, the event-time kind is recorded as
`hirid_last_map_hr_proxy`, and the ICU-end kind is recorded as
`hirid_last_observation_proxy`. These are operational proxies, not confirmed
clinical death or discharge timestamps. The last MAP/heart-rate proxy and the
last-observation ICU-end proxy can disagree because they are derived from
different available observations and processing paths.

## G. Temporal precision and discretization

Mortality metadata is extracted with `event_interval = mins(1L)`. The ricu
interval conversion floors timestamps to the target interval. For example:

- 25h00m30s becomes 25h00m and may be excluded as occurring at the landmark;
- 37h00m30s becomes 37h00m and may be labeled positive at the inclusive upper
  boundary.

The source metadata records:

- `event_time_precision_minutes = 1`;
- `event_time_discretized = TRUE`;
- `event_time_kind`, distinguishing MIMIC recorded admission death time from
  the HiRID proxy;
- `icu_end_kind`, distinguishing MIMIC ICU end from the HiRID proxy.

This flooring creates a boundary minute in which the exact ordering of death
and landmark cannot be recovered. It is accepted because the research question
concerns measurement-frequency shift rather than second-level mortality timing.
The interval comparison is consistently applied to the discretized timestamp.

Discretizing labels does not add future measurements to the model input grid.
Feature extraction is independently truncated at the prediction start. It can,
however, affect eligibility or the label when a death occurs within the minute
containing a boundary. This is a small temporal-label approximation, not
evidence that the clinical outcome definition is exact. Later real-data
validation should count deaths near both landmark and horizon boundaries.

## H. Measurement-frequency processing

The configurable task extracts the same dynamic concept list at the requested
frequency: 1h, 15min, or 5min. It reuses `load_step()` and ricu concept loading,
then maps the result to the truncated grid with `map_to_grid()`.

Where a numeric ricu concept specifies median aggregation, values in a target
bin are median-aggregated. The exact aggregation remains concept-specific and
is not replaced by a new study-specific reducer. Missing bins remain missing
after cohort construction. No interpolation is added by this pipeline.

The YAIB preprocessing/model stage may later impute, scale, or otherwise
transform features. Those operations are distinct from cohort construction and
must be described separately in model experiments.

Labels and source metadata are frequency-independent. Only the dynamic feature
grid and its aggregation interval change across 1h, 15min, and 5min outputs.

## I. Static predictors and potential leakage

The configurable mortality task supplies these static predictors:

- `age`;
- `sex`;
- `height`;
- `weight`.

The configured source mappings are approximately:

- HiRID: age and sex from `general`; height and weight from observation
  variable IDs 10000450 and 10000400;
- MIMIC-IV: age and sex from `patients` (`anchor_age`, `gender`); height and
  weight from `chartevents` item IDs 226707 and 226512.

The code does not impose a per-variable timestamp cutoff on static extraction.
Age and sex are source-level demographic fields and are ordinarily interpreted
as baseline attributes. Height and especially weight are measurement concepts
whose source records are not proven by this code to precede every landmark.
Their availability and timing should therefore be audited in real data before
claiming strict prospective no-leakage for those static variables.

Outcome metadata, ICU start/end metadata, LOS, discharge status, death times,
and label-reason fields are not written to `dyn.parquet` or `sta.parquet`.
Output validation rejects those columns if they appear among model features.

## J. Source-specific differences and threats to validity

MIMIC-IV uses hospital admission death information combined with a
last-care-unit rule and an explicit hospital-to-ICU ID mapping. HiRID uses a
discharge status plus observation-derived proxies. These are not the same
clinical measurement process.

Important consequences include:

- MIMIC has a recorded `deathtime` field, but ICU mortality is still an
  operational attribution rule rather than a universally available direct ICU
  death field;
- HiRID's event and ICU-end times are proxies and may be missing or disagree;
- measurement density and documentation practices differ across hospitals;
- canonical base-cohort eligibility can select stays using information after
  the landmark;
- the same label name can therefore represent different source-specific
  operational outcomes;
- performance differences cannot automatically be attributed solely to
  measurement frequency.

The prediction unit is `stay_id`. YAIB's generic splitting code uses the
configured grouping variable, normally `stay_id`, and the processed outputs do
not carry a patient identifier for enforcing patient-level separation. Patients
with multiple ICU stays may therefore require an explicit patient-level split
policy before leakage-sensitive analyses. This task does not redesign YAIB's
splitter.

## K. Reproducibility and provenance

The source metadata cache is independent of W, H, and feature frequency:

```text
<out_dir>/mortality_metadata/hirid/
    outcome_metadata.parquet
    provenance.json

<out_dir>/mortality_metadata/miiv/
    outcome_metadata.parquet
    provenance.json
```

Each W/H task writes its standard YAIB files under a W/H-specific directory:

```text
<out_dir>/mortality_w24_h12/hirid/
    dyn.parquet
    sta.parquet
    outc.parquet
    attrition.csv
    task_provenance.json
```

Non-hourly outputs use the existing source-frequency suffix, such as
`hirid_15min` or `miiv_5min`.

Metadata provenance includes the source, one-minute extraction interval,
flooring policy, configuration fingerprint, ricu version, source metadata
pipeline files, and a shared canonical fingerprint. The tracked metadata files
include the landmark entrypoint/helper, `src/steps.R` and frequency helpers,
mortality callback, and outcome concept dictionary. Canonical base-cohort provenance is
kept separate and its existing fingerprint behavior is unchanged.

The task provenance records the source metadata provenance in addition to W, H,
frequency, observation convention, and canonical base provenance. Metadata and
provenance must exist together; incompatible fingerprints are rejected rather
than silently reused. Label construction copies source metadata before adding
horizon-specific `reason` and `label` fields.

Example commands, after a valid ricu data configuration and canonical base
cohort exist:

```bash
cd /home/mingzhul/projects/Simultaneous-EHR/repos/YAIB-cohorts/R

Rscript base_cohort.R --src hirid --frequency 1h
Rscript mortality_landmark.R --src hirid --frequency 1h \
  --observation-hours 24 --prediction-hours 12
Rscript mortality_landmark.R --src hirid --frequency 15min \
  --observation-hours 24 --prediction-hours 12
Rscript mortality_landmark.R --src miiv --frequency 1h \
  --observation-hours 36 --prediction-hours 12
```

The current checkout has no configured HiRID or MIIV source data and therefore
has not generated real cohorts.

## L. Heuristics and compromises summary

| Design choice | Ideal approach | Implemented approach | Reason | Possible consequence | Validation or sensitivity analysis |
|---|---|---|---|---|---|
| W+1-hour observation convention | Define a landmark by exact elapsed duration | W is the last included hourly-bin index; start is W+1 | Preserve YAIB compatibility | W=24 means `[0,25)`, which can be misread as 24 hours | Synthetic grid tests for W24 and W36 at all frequencies |
| One-minute mortality resolution | Preserve exact source timestamp | Floor event time to one minute | Measurement-frequency study does not require seconds | Boundary-minute eligibility/label ambiguity | Synthetic 24:59:59, 25:00:00, 25:00:01, 36:59:59, 37:00:00, 37:00:01 tests; later boundary counts recommended |
| HiRID death proxy | Use a recorded clinical death timestamp | Last MAP/heart-rate observation plus dead discharge status | Existing YAIB/HiRID operational definition | Proxy may be delayed, missing, or disagree with actual death | Metadata kind fields; compare alternative proxies later if feasible |
| HiRID ICU-end proxy | Use recorded ICU discharge time | Last-observation proxy from existing stay processing | Preserve existing pipeline | Eligibility may differ from true discharge | Audit proxy disagreement in real data |
| MIMIC-IV last-care-unit attribution | Use an explicit ICU death field | Hospital death plus transfer history mapped from `hadm_id` to `stay_id`; final ICU care unit required | Correct ICU-stay attribution while reusing callback | Depends on transfer mapping and operational final-unit rule | Source inspection and synthetic wrapper/core tests; full MIIV mapping remains unexecuted |
| Canonical base eligibility | Select using only data available at each landmark | Reuse canonical hourly seven-day base IDs | YAIB compatibility and comparability | Post-landmark information can affect selection | Compare with a landmark-specific cohort later |
| Alive discharge negative | Treat discharge as censoring or competing risk | Eligible alive discharge during horizon is label 0 | Binary mortality target requires a negative class | Competing events are collapsed into no ICU death | Report discharge attrition/prevalence; consider competing-risk analysis later |
| Unknown outcome exclusion | Resolve outcome state from additional source data | Exclude unknown/missing status | Avoid inventing labels | Reduces sample size and may alter case mix | Track attrition by reason |
| Frequency-independent labels | Reconstruct labels separately per frequency | Reuse one-minute source metadata for all feature frequencies | Isolate measurement-frequency shift | Any source metadata error affects every frequency | Cross-frequency ID/label/prevalence invariance tests |
| ricu aggregation and missingness | Use raw values with a fully specified reducer | Reuse concept-specific ricu aggregation; missing bins remain missing | Avoid duplicate preprocessing | Concept-specific reducers and missingness may affect comparisons | Inspect concept configuration; model-stage imputation is separate |
| Static-feature timing | Prove every feature is available before the landmark | Use configured age, sex, height, weight without a new cutoff | Preserve existing YAIB feature set | Height/weight timing may not be strictly prospective | Audit source timestamps and run static-feature sensitivity analyses |
| Multiple ICU stays and splitting | Split by patient and prevent all patient overlap | Output stay IDs; generic YAIB grouping is normally stay-level | Reuse YAIB interfaces | Same patient can span splits unless configured otherwise | Add patient-level split analysis before transfer-learning claims |
| Source metadata caching/provenance | Recompute or version every extraction artifact | Cache once per source with code/config/ricu fingerprints | Reproducibility without repeated extraction | Fingerprint scope must stay aligned with extraction dependencies | Temporary-file invalidation tests and provenance files |

## M. Recommended future sensitivity analyses

The following are not implemented in this task:

- exclude deaths within a prespecified number of minutes of either boundary;
- compare alternative HiRID MAP/heart-rate proxy definitions;
- compare benchmark-compatible eligibility with landmark-only eligibility;
- repeat analyses for multiple W/H combinations;
- report prevalence and every exclusion reason by hospital and frequency;
- enforce patient-level rather than stay-level train/validation/test separation;
- quantify measurement density and missingness within the eligible cohort;
- perform a real-data regression comparison of legacy and corrected MIIV
  mortality24 outputs;
- execute the full MIIV ricu ID map on an approved source-backed validation
  subset.

These analyses are important before interpreting cross-hospital transfer or
measurement-frequency effects as causal or purely methodological.
